# 秒写后端 · 前端对接指南

本文档面向**微信小程序 / 前端**，说明与 `miaoxie-server` 对接时的**强制要求**、**推荐调用顺序**及**常见错误**（如 `缺少必要参数: signature`）。

**基准地址**：`https://<你的域名>` 或本地 `http://localhost:<PORT>`（默认 `PORT` 见服务端环境变量，常见 `3000`）。

**通用请求头**：

- `Content-Type: application/json`（凡带 JSON Body 的接口）
- 需登录的接口：`Authorization: Bearer <token>`（`<token>` 为登录接口返回的 JWT 字符串，**不要**加引号）

**通用响应**：业务上成功时通常 `code === 0`，数据在 `data`；失败时 `code !== 0`，`message` 为说明（部分错误带 `requestId`）。

---

## 一、为什么会出现 `400` +「缺少必要参数: xxx」？

登录接口 `POST /api/auth/login` 在**非 Mock** 路径下，会执行**固定五项必填校验**（见 `src/controllers/authController.ts` → `validateLoginParams`）：

| 字段 | 说明 |
|------|------|
| `code` | 必须**非空**（`wx.login` 返回的 `code`） |
| `rawData` | 必须**非空** |
| `signature` | 必须**非空** |
| `encryptedData` | 必须**非空** |
| `iv` | 必须**非空** |

后端用 `if (!data[field])` 判断：**缺字段、`undefined`、空字符串 `""`、仅空格（若未 trim）都会失败**。  
因此若请求体里**没有 `signature` 字段**，或 `signature: ""`，就会得到：

```json
{"code":400,"message":"缺少必要参数: signature"}
```

同理可出现 `缺少必要参数: rawData` / `encryptedData` / `iv` 等。

### 正式环境（真机 / 体验版）应该怎么传？

微信侧需要能在同一次登录会话里提供 **`rawData` + `signature` + `encryptedData` + `iv`** 的来源，常见来源包括：

- 历史上 **`wx.getUserInfo`** / **`wx.getUserProfile`** 的返回（含加密字段）；
- 或微信文档中与 **`session_key` 配套的用户信息加密包**（需与**当前** `wx.login` 的 `code` **同一会话**内获取）。

**调用顺序（必须）**：

1. 先 **`wx.login` → 拿到 `code`**（一次 `code` 仅一次有效，且与后续加密数据会话绑定）。
2. 再在**同一轮流程**内获取用户信息相关加密字段（或使用后端认可的字段来源）。
3. 将 **`code` 与上述五项一并 POST** 给 `/api/auth/login`。

若产品形态改为**仅**「`chooseAvatar` + `input type=nickname`」、**没有**微信下发的 `encryptedData` / `signature` 等，则**当前后端校验无法通过**，需要**产品/后端另定方案**（例如：单独只传 `code` + 明文昵称头像的登录协议升级，或联调阶段使用下文 Mock）。

## 二、登录接口 `POST /api/auth/login`

### 2.1 路径与方法

- **URL**：`/api/auth/login`
- **方法**：`POST`
- **认证**：不需要 Bearer

### 2.2 请求体（两种场景）

#### A. 联调 / 自动化（Mock）

当 `code` **以 `test_` 开头**时，走服务端 Mock：**不校验** `rawData`、`signature`、`encryptedData`、`iv`。

只需传：

| 字段 | 必填 | 说明 |
|------|------|------|
| `code` | 是 | 例如 `test_myapp_001`（必须以 `test_` 开头） |
| `nickName` | 否 | 测试昵称 |
| `avatarUrl` | 否 | 测试头像 URL |

**示例**：

```json
{
  "code": "test_local_001",
  "nickName": "测试用户",
  "avatarUrl": "https://example.com/a.png"
}
```

#### B. 生产 / 真机微信登录（非 Mock）

**必须同时传齐下面 5 个字段，且每个都是非空字符串**：

| 字段 | 说明 |
|------|------|
| `code` | `wx.login` 返回 |
| `rawData` | 与微信用户信息接口配套 |
| `signature` | 同上 |
| `encryptedData` | 服务端用 `session_key` 解密昵称/头像 |
| `iv` | 解密用 |

**可选**（强烈建议传，作兜底）：

| 字段 | 说明 |
|------|------|
| `nickName` | 明文昵称；当解密失败或解密昵称为占位「微信用户」时作为库初始值 |
| `avatarUrl` | 明文头像 URL（如自建 COS）；同上 |

**示例结构（字段值需替换为真实内容）**：

```json
{
  "code": "081XXXX",
  "rawData": "{...}",
  "signature": "xxxxxxxx",
  "encryptedData": "yyyyyyyy",
  "iv": "zzzzzzzz",
  "nickName": "用户起的昵称",
  "avatarUrl": "https://你的存储/头像.png"
}
```

### 2.3 服务端行为摘要

- 用 `code` 换 `session_key`，再解密 `encryptedData`；若解密失败或昵称为「微信用户」，**仅以请求体** `nickName` / `avatarUrl` 写入数据库。
- 成功后返回 `data.token`（JWT）与 `data.userInfo`（库表最新数据）。

### 2.4 成功响应示例

```json
{
  "code": 0,
  "message": "Success",
  "data": {
    "token": "eyJhbGciOi...",
    "userInfo": {
      "id": 1,
      "openid": "oXXXX",
      "nickName": "展示用昵称",
      "avatarUrl": "https://...",
      "isAdmin": false
    }
  }
}
```

### 2.5 头像域名（小程序）

若 `avatarUrl` 使用微信域名（如含 **`thirdwx.qlogo.cn`**），请到**微信公众平台 → 开发 → 开发管理 → 服务器域名 → downloadFile 合法域名**中添加对应域名，否则组件无法下载图片。

## 三、Token 与鉴权

- JWT **放在请求头**：`Authorization: Bearer <token>`（注意 `Bearer` 后有一个空格）。
- Token 由登录或刷新接口获得；其它业务接口若返回 `401`，先 **refresh** 或重新 **login**。

---

## 四、`POST /api/auth/refresh`

- **Header**：`Authorization: Bearer <当前 token>`
- **Body**：一般无需 Body
- **成功**：`code === 0`，`data.token` 为新 token

---

## 五、`GET /api/auth/verify`

- **Header**：`Authorization: Bearer <token>`
- **成功**：`data.openid` 为当前用户 openid

---

## 六、资料更新 `PUT /api/user/update`

用于登录后修改昵称、头像（不依赖登录时的加密包）。

- **URL**：`/api/user/update`
- **方法**：`PUT`
- **Header**：
  - `Content-Type: application/json`
  - `Authorization: Bearer <token>`

**Body**（`nickName`、`avatarUrl` **至少传一个**）：

```json
{
  "nickName": "新昵称",
  "avatarUrl": "https://你的域名/新头像.png"
}
```

**长度限制**：昵称 ≤ 64 字符；头像 URL ≤ 2048 字符（建议库表 `avatar_url` 为 `TEXT`，见 `scripts/sql/alter-users-avatar-url-text.sql`）。

**成功示例**：

```json
{
  "code": 0,
  "message": "更新成功",
  "data": {
    "id": 1,
    "openid": "oXXXX",
    "nickName": "新昵称",
    "avatarUrl": "https://...",
    "isAdmin": false
  }
}
```

身份依据 Token 内的 **`openid`** 更新数据库，**不是**数字 `userId`。

## 七、排错清单

| 现象 | 可能原因 | 处理 |
|------|----------|------|
| `缺少必要参数: signature`（或其它四项之一） | 非 Mock 时未传齐五项，或某字段为空字符串 | 按第二节 B 传齐；联调可临时用 `test_` 前缀 Mock |
| `缺少必要参数: rawData` | 同上 | 同上 |
| `401` + 获取会话信息失败 | `code` 过期、重复使用，或与加密数据不同步 | 重新 `wx.login` 拿新 `code`，并重新拉加密字段 |
| 解密后仍显示「微信用户」 | 微信隐私策略占位 | 传明文 `nickName`/`avatarUrl` 或使用 `PUT /api/user/update` |
| 头像不显示 | 域名未加入 downloadFile 白名单，或 URL 无效 | 配置小程序域名；COS 链接需 https 可访问 |

## 九、客户端诊断日志（直播页等）

用于直播页管线不稳定、高光录制失败等场景的**结构化上报**，便于后端按 `diag.matchId`、`reason`、`logs` 内事件码聚合分析。

### 9.1 `POST /api/client/diagnostic-log`

- **认证**：**不强制**登录；若携带有效 `Authorization: Bearer <token>`，服务端会将 `openid` 一并落库，便于关联用户。
- **Header**：
  - `Content-Type: application/json`
  - 可选设备信息（会与 Body `device` 合并进库表 `device_json`）：`X-Client-Device`、`X-Device-Info`、`X-Wx-Client-Version`（大小写不敏感，与小程序 `header` 习惯一致即可）。
- **Body 字段**：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `at` | number | 是 | 客户端毫秒时间戳 |
| `reason` | string | 是 | 触发标签，如 `segment_start_fail_storm_cycle` |
| `device` | object \| string | 否 | 机型 / 系统 / 微信版本等；也可依赖上文自定义 Header |
| `diag` | object | 是 | 管线快照（建议含 `matchId`、rolling 会话、是否录中、`rollingFsBusy`、健康度等） |
| `logs` | array | 是 | 环形缓冲；服务端**仅保留至多约 80 条**（取数组**尾部**） |

**请求体示例**：

```json
{
  "at": 1713686400123,
  "reason": "segment_start_fail_storm_cycle",
  "device": {
    "model": "iPhone 15",
    "system": "iOS 17.4",
    "wxVersion": "8.0.xx",
    "libVersion": "3.4.5"
  },
  "diag": {
    "matchId": "match_abc_001",
    "rollingSessionId": "rs_1",
    "isRecording": true,
    "rollingFsBusy": false,
    "healthScore": 0.72
  },
  "logs": [
    { "t": 1713686400100, "e": "segment_start_err", "errMsg": "..." },
    { "t": 1713686400110, "e": "fs_warn", "level": "warn" }
  ]
}
```

**成功响应示例**（`code === 0`）：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "id": 42,
    "requestId": "wx-xxxx"
  }
}
```

- `data.id`：MySQL 自增主键，可与服务端 **`logs/combined.log`** 中关键字 `diagnostic_log_ingested` 对照（同条记录会带 `diagnosticLogId`）。
- 响应头通常含 **`X-Request-ID`**，可与运维日志、DB 中 `request_id` 字段联查。

**库表与迁移**：首次部署请在目标库执行 `scripts/sql/client-diagnostic-log-migration.sql` 创建表 `client_diagnostic_logs`。

**聚合分析（示例）**：落库后可在数仓或 MySQL 中按 `match_id`、`reason` 分组统计；若需展开 `logs_json` 内事件码 `e`，可使用 MySQL 8+ 的 `JSON_TABLE` 等函数按行展开后再聚合。

## 十、上传诊断日志后如何快速取数调试（尽量少开发）

优先用**现成工具**，无需再写前端页面：

1. **直连 MySQL（推荐，零代码）**  
   使用 TablePlus / DBeaver / Navicat / 命令行 `mysql` 连接业务库，查表 `client_diagnostic_logs`。常用条件：`match_id = '...'`、`reason = '...'`、`id = <上传返回的 data.id>`、`created_at` 时间范围。

2. **grep 服务日志文件**  
   若进程将日志写到仓库下 `logs/combined.log`（见 `src/utils/logger.ts`），可在服务器上执行：  
   `grep diagnostic_log_ingested logs/combined.log`  
   或按返回的 `diagnosticLogId`、`matchId` 过滤；适合与 `X-Request-ID` 串联排障。

3. **管理员 HTTP 接口（已内置，需管理员账号 JWT）**  
   - `GET /api/admin/diagnostic-logs?matchId=&reason=&openid=&limit=30`：摘要列表（不含大 JSON）。  
   - `GET /api/admin/diagnostic-logs/:id`：单条完整 `device` / `diag` / `logs`。  
   可用 curl、Postman、VS Code REST Client 调用，**limit 最大 100**。

云上部署时，若日志已采集到 **阿里云 SLS / 腾讯云 CLS / Datadog** 等，用平台检索 `diagnostic_log_ingested` 或 `requestId` 同样可快速定位。

## 十一、赛事直播雷达（Sync Lab）— 小程序端 `/api/app/*`

本子系统与上文秒写业务接口**响应格式不同**：成功为 `success: true`，失败为 `success: false` + `error_code` + `message` + `timestamp`（详见设计说明书）。**不影响**既有 `code === 0` 接口。

**部署前置**：

1. MySQL 执行 `scripts/sql/sync-lab-radar-migration.sql`
2. 配置 `REDIS_URL`（本地 Redis，勿公网暴露）
3. 服务端 `.env` 配置 `RADAR_API_SECRET`（与雷达端 Spider 本地密钥一致）

维护赛事、场次、主播及场次-主播绑定。`action` 取值：

| action | 说明 |

| `upsert_match` | 新建/更新场次（不含主播），`data` 含 `tournament_id`、`team_a`、`team_b`、`start_time` |

成功示例：

```json
}
```

### 11.2 `POST /api/app/match/add_task`

挂载抖音口令/链接，压入雷达任务队列（同一场次可多次调用以挂载多路直播）。

**重要**：为避免服务端 IP 被抖音封锁，**服务端不再访问抖音 HTTP**。口令只做本地正则解析；完整主播信息（`sec_user_id`、可进房 `live_url`）由**雷达浏览器进房后一次性上报**（见 12.2 `report_anchor_meta`）。

```json
{
  "match_id": 8888,
  "raw_text": "7@5.com ... https://v.douyin.com/xxx/"
}
```

**挂载流程**：

1. 服务端本地从口令提取：分享链接、`【昵称】` 提示、（若文本内已有）`sec_user_id`
2. 按 `mount_fingerprint`（归一化分享链接）去重后任务入队
3. 若口令内**已含** `sec_user_id`：立即写入 `anchors` 并绑定场次（仍不访问抖音）
4. 若仅短链：返回 `anchor_resolve_status: "pending_radar"`，等雷达 `report_anchor_meta` 后入库

成功时返回（短链场景示例）：

```json
{
  "success": true,
  "match_id": 8888,
  "task_enqueued": true,
  "anchor_resolve_status": "pending_radar",
  "share_url": "https://v.douyin.com/Dr0CbDBmsJQ",
  "mount_fingerprint": "v.douyin.com/dr0cbdbmsjq",
  "anchor_name": "超哥（永安红）",
  "message": "Task queued; anchor profile will be resolved once by radar browser."
}
```

| 字段 | 说明 |
|------|------|
| `anchor_resolve_status` | `pending_radar`（待雷达解析）/ `resolved`（口令内已有 sec_user_id） |
| `mount_fingerprint` | 分享链接去重指纹 |
| `share_url` | 口令中的分享链接 |
| `sec_user_id` / `live_url` | 仅 `resolved` 时有值 |

**去重规则**：

| 场景 | `task_enqueued` | `duplicate_reason` |
|------|-----------------|-------------------|
| 同分享链接已在队列 | `false` | `queue_pending` |
| 同 sec_user_id 已在队列 | `false` | `queue_pending` |
| Failover 重投待认领 | `false` | `failover_pending` |
| 该路已在监控中 | `false` | `already_monitoring` |
| 正常入队 | `true` | — |

> 联调兜底：若必须让服务端 HTTP 解析短链，可设环境变量 `SYNC_LAB_SERVER_DOUYIN_HTTP_RESOLVE=true`（**生产不推荐**，有 IP 被封风险）。

### 11.3 `POST /api/app/match/stop_monitoring`

关闭该场次**全部直播间**的监控任务（清除待领队列、释放占用 Worker、汇总统计数据）。

```json
{
  "match_id": 8888
}
```

| 字段 | 说明 |
|------|------|
| `match_status` | 固定为 `ended` |
| `end_reason` | 固定为 `force_stopped_by_user` |
| `queue_tasks_removed` | 从 Redis 队列移除的待领任务数 |
| `workers_released` | 被释放为 idle 的 Worker ID 列表（含虚拟 Worker） |
| `anchors_settled` | 各路主播结算摘要；`stats_source` 为 `radar_report`（雷达已交单）或 `stream_fallback`（后端从流水兜底） |
| `peak_user_count` / `total_viewers_recap` / `duration_seconds` | 场次聚合统计（写入 `matches` 表） |

已结束场次再次调用返回 `409` + `MATCH_ALREADY_ENDED`。

### 11.4 `POST /api/app/match/reopen_monitoring`

重开已结束（或异常残留）的场次监控。**不要**仅手动改 MySQL 的 `match_status`：Redis 中主播 `settled` 快照仍在时，看门狗会在约 10 秒内通过级联结赛逻辑把状态改回 `ended`。应调用本接口一次性清理残留并重新入队。

```json
{
  "match_id": 8888,
  "requeue_anchors": true,
  "clear_streams": false,
  "reset_stats": false,
  "force": false
}
```

| 请求字段 | 默认 | 说明 |
|----------|------|------|
| `match_id` | 必填 | 场次 ID |
| `requeue_anchors` | `true` | 是否为已绑定主播重新入队雷达任务 |
| `clear_streams` | `false` | 是否同时清空 Redis `stream` / `room_cumulative` 键 |
| `reset_stats` | `false` | 是否重置 `peak_user_count` / `total_viewers_recap` / `duration_seconds` |
| `force` | `false` | 强制重开；`monitoring` / `waiting_radar` 状态下清理脏数据时需传 `true` |

**响应字段**：

| 字段 | 说明 |
|------|------|
| `match_status` | 固定为 `waiting_radar` |
| `end_reason` | 固定为 `null` |
| `previous_status` | 重开前的场次状态 |
| `settled_keys_cleared` | 已删除的 Redis settled 快照数 |
| `stream_keys_cleared` | 已删除的 stream 键数（仅 `clear_streams=true` 时 > 0） |
| `room_cumulative_keys_cleared` | 已删除的 room_cumulative 键数 |
| `queue_tasks_removed` | 从队列移除的待领任务数 |
| `workers_released` | 被释放为 idle 的 Worker ID 列表 |
| `tasks_requeued` | 各路主播重入队结果；`task_enqueued=false` 时见 `skip_reason`（`missing_live_url` / `queue_pending`） |

**允许重开的状态**：

| 场景 | 是否需 `force` |
|------|----------------|
| `ended` / `interrupted` | 否 |
| `monitoring` / `waiting_radar`（如仅改了 DB、Redis settled 仍在） | 是 |

错误码：`404` + `MATCH_NOT_FOUND`；`409` + `MATCH_CANNOT_REOPEN`（进行中场次未传 `force`）。

### 11.5 `GET /api/app/match/stream_data?match_id=8888`

返回该场次**多路主播合并累加**后的时序曲线，供大屏轮询（建议 15~30 秒）。

| 字段 | 说明 |
|------|------|
| `match_status` | `waiting_radar` / `monitoring` / `ended` / `interrupted` |
| `timeline_data` | `[{ "timestamp": 1779353590, "user_count": "4500" }, ...]` |
| `current_online_count` | 合并时序最后一点（各路 **前向填充** 后累加，避免多直播间上报时间错开时只显示最近一路） |
| `peak_user_count` | 已归档峰值或实时合并峰值 |
| `total_viewers_recap` | **累计场观**；监控中从 Redis 按 room_id 实时汇总（同 room MAX、异 room SUM），已结赛读 MySQL |

### 11.6 `GET /api/app/tournament/influence?tournament_id=101`

完赛影响力战报：聚合峰值、累计场观、`influence_score` 及场次排行 `rankings_by_popularity`。

## 十二、赛事直播雷达 — 雷达端 Spider `/api/spider/*`

**认证**：免 JWT，使用 HMAC 请求头（与 `RADAR_API_SECRET` 配套）。

| Header | 说明 |
|--------|------|
| `X-Radar-WorkerID` | 设备 ID，如 `mac_air` |
| `X-Radar-Timestamp` | 10 位 Unix 秒级时间戳，与服务端差 ±60 秒内 |
| `X-Radar-Nonce` | 8~16 位随机串 |
| `X-Radar-Signature` | `HMAC_SHA256(secret, WorkerID + Timestamp + Nonce + BodyText)` 小写十六进制；`BodyText` 为**原始 JSON 字符串** |

**签名示例（Node）**：

```javascript
const crypto = require('crypto');
const workerId = 'mac_air';
const timestamp = String(Math.floor(Date.now() / 1000));
const nonce = 'a1b2c3d4e5f6';
const bodyText = JSON.stringify({ worker_id: workerId });
const sig = crypto
  .createHmac('sha256', process.env.RADAR_API_SECRET)
  .update(workerId + timestamp + nonce + bodyText)
  .digest('hex');
```

**节点自动注册与心跳**：所有 `/api/spider/*` 在 HMAC 鉴权通过后，服务端会按请求头 `X-Radar-Worker-ID` 自动 **Upsert** 表 `radar_workers`（新设备 `status=idle`；已存在仅刷新 `last_seen_at`）。领单成功 → `busy` + `current_match_id`；`report_end` 成功 → `idle` + 清空 `current_match_id`。迁移脚本：`scripts/sql/radar-workers-migration.sql`。

**Worker ID**：由雷达端本地生成（如 `mac_air` 或 `asus_win_20260522`），写入 Header `X-Radar-Worker-ID`，无需事先在后台手工录入。

### 12.1 `POST /api/spider/fetch_task`

每 3 秒轮询领单。Body：`{"worker_id":"mac_air"}`（建议与 Header 一致）。

有任务时 `has_task: true`。`task` 关键字段：

| 字段 | 说明 |
|------|------|
| `anchor_resolve_status` | `pending_radar` 时需先 `report_anchor_meta` |
| `raw_share_text` | 口令原文，优先用它打开浏览器 |
| `share_url` / `live_url` | 待解析时为分享短链；解析后为进房 URL |
| `mount_fingerprint` | 与 `report_anchor_meta` 对齐 |
| `anchor_name` | 口令内 `【昵称】` 提示（可为空） |

示例（短链待解析）：

```json
{
  "success": true,
  "has_task": true,
  "task": {
    "match_id": 8888,
    "tournament_id": 101,
    "sec_user_id": "",
    "live_url": "https://v.douyin.com/Dr0CbDBmsJQ",
    "anchor_name": "超哥（永安红）",
    "raw_share_text": "#在抖音... https://v.douyin.com/Dr0CbDBmsJQ/ ...",
    "mount_fingerprint": "v.douyin.com/dr0cbdbmsjq",
    "anchor_resolve_status": "pending_radar",
    "poll_interval_sec": 30
  }
}
```

### 12.2 `POST /api/spider/report_anchor_meta`（新增，必接）

**调用时机**：雷达用浏览器打开 `raw_share_text` / 分享链接并完成**首次进房**后，**只调用一次**，然后再开始 `report_stream` 轮询。

**作用**：将浏览器内解析到的主播信息上报服务端入库（`anchors` + `match_anchor_relations`），服务端不做任何抖音 HTTP 请求。

Body 必填：

| 字段 | 说明 |
|------|------|
| `match_id` | 与 task 一致 |
| `sec_user_id` | 页面/跳转 URL 中的真实抖音 ID（`MS4wLjAB...`） |
| `anchor_name` | 主播昵称 |
| `live_url` | 可进房的直播间 URL（如 `https://live.douyin.com/{room_id}`） |
| `mount_fingerprint` | 与领单 task 一致（推荐，便于对账） |
| `room_id` | 可选，抖音直播间 ID；推荐与 `live_url` 路径段一致 |

```json
{
  "worker_id": "mac_air",
  "match_id": 8888,
  "mount_fingerprint": "v.douyin.com/dr0cbdbmsjq",
  "sec_user_id": "MS4wLjABAAAADK8Y726omYtEplqE0ocblSgDFUbv4h5ciXsqeOwQ4c0",
  "anchor_name": "超哥（永安红）",
  "live_url": "https://live.douyin.com/7642669453867617075",
  "room_id": "7642669453867617075"
}
```

成功响应：

```json
{
  "success": true,
  "match_id": 8888,
  "sec_user_id": "MS4wLjABAAAADK8Y726omYtEplqE0ocblSgDFUbv4h5ciXsqeOwQ4c0",
  "anchor_name": "超哥（永安红）",
  "live_url": "https://live.douyin.com/7642669453867617075",
  "anchor_created": true,
  "anchor_bound": true,
  "resolve_source": "radar_browser",
  "message": "Anchor profile ingested from radar browser successfully."
}
```

**雷达端推荐时序**：

```
fetch_task → 浏览器打开 raw_share_text → 提取 sec_user_id/昵称/live_url/room_id
  → report_anchor_meta（一次） → 循环 report_stream → report_end
```

**雷达端伪代码（Python）**：

```python
task = fetch_task()
if not task or not task.get("has_task"):
    return

raw = task["task"].get("raw_share_text") or task["task"]["live_url"]
page = browser.open(raw)  # 雷达已有 Playwright/Selenium

sec_user_id = page.extract_sec_uid()      # 从 URL 或页面 JSON
anchor_name = page.extract_nickname() or task["task"].get("anchor_name")
live_url = page.canonical_live_url()

report_anchor_meta({
    "worker_id": WORKER_ID,
    "match_id": task["task"]["match_id"],
    "mount_fingerprint": task["task"].get("mount_fingerprint"),
    "sec_user_id": sec_user_id,
    "anchor_name": anchor_name,
    "live_url": live_url,
})

while monitoring:
    report_stream(
        match_id=...,
        sec_user_id=sec_user_id,
        user_count=...,
        timestamp=...,
        room_id=room_id,
        cumulative_viewers=...,
    )
```

### 12.3 `POST /api/spider/report_stream`

Body 必填：`match_id`、`sec_user_id`、`user_count`（原样字符串如 `"1.2w"`）、`timestamp`（秒）。**须先完成 12.2**，否则返回 `ANCHOR_NOT_BOUND`。

Body 可选（**Radar 新版本推荐携带**）：

| 字段 | 说明 |
|------|------|
| `room_id` | 抖音直播间 ID；同一次直播断线重连不变，关播重开会变 |
| `cumulative_viewers` | 抓包得到的当前累计观看人数（如 `"8.4w"`） |

服务端按 `match_id + sec_user_id + room_id` 维护 Redis Hash：**同一 room_id 取 MAX**（防断线重连重复累计），**不同 room_id 再 SUM**（防关播重开丢数据）。小程序 `match/list`、`match/detail`、`stream_data` 在监控中会实时读取汇总后的 `total_viewers_recap`。

```json
{
  "worker_id": "mac_air",
  "match_id": 8888,
  "sec_user_id": "MS4wLjABAAAADK8Y726omYtEplqE0ocblSgDFUbv4h5ciXsqeOwQ4c0",
  "user_count": "1.2w",
  "timestamp": 1779353590,
  "room_id": "7642669453867617075",
  "cumulative_viewers": "8.4w"
}
```

> 未携带 `room_id` / `cumulative_viewers` 时，服务端保持旧逻辑，仅在 `report_end` 时用 `total_viewers_recap` 覆盖结算。

### 12.4 `POST /api/spider/worker_init`

雷达**开机首请求**（建议先于 `fetch_task`）：无条件将 DB 中该 Worker 置为 `idle`、清空 `current_match_id` 与 Redis 任务分配快照。Body 可为 `{}` 或 `{"worker_id":"..."}`（与 Header 一致）。

### 12.5 `POST /api/spider/report_end`

Body 必填：`match_id`、`sec_user_id`、`duration_seconds`、`end_reason`。

Body 可选（推荐）：`room_id`、`cumulative_viewers`（与流水规则一致；交单时还会与 `total_viewers_recap` 取 **MAX** 后写入 room Hash）。

| `end_reason` | 行为 |
|--------------|------|
| `worker_interrupted` | Worker 中断；**仅 merge room 累计场观，不写终态 settled**，该路可 Failover 重连后继续上报；其它路继续监控 |
| `force_stopped_by_user` | 用户手动中止；**立即**结束整场（建议优先调用小程序 `stop_monitoring`） |
| `stream_closed` 等 | 写入该路终态 settled；多主播全部交单后 `ended` |

服务端内置看门狗（每 10 秒）：心跳超 15 秒 → 按**单路** Failover 重投，多路场次不会误杀其它直播间；Failover 10 分钟无人领 → 仅结算该路；场次监控超 4 小时 → `duration_limit_reached` 整场结赛。若需重开已结束场次，请调用小程序 `reopen_monitoring`，勿仅改数据库。
