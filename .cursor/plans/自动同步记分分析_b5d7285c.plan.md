# 自动同步记分实现梳理与优化建议（修订版）

## 0. 产品约束（本轮已对齐）

- **核心目标**：单场比赛约 2–3 小时、一晚直播约 4–5 小时场景下，**采集端必须尽量稳定**；**直播端已承担相机渲染 + 抖音录屏，不能再加压**。
- **「稳定再提交」类建议已撤回/改写**：见下文 §4.1，避免重复历史上与 24 秒、回表、清零改分相关的可用性问题。
- **文案**：不强制改「敬请期待」等文案；若要做体验收敛，倾向 **仅白名单用户** 在 Live 暴露「长按节次 → 自动记分」能力，普通用户无入口（无感）。
- **比分 >255**：**不支持**，不扩展协议。

## 3. 客观评估（摘要）

- 工程上 BLE 单例 + 协议 CRC + Live 节流是合理基线。
- 风险主要在 **长时采集**（VK 会话、相机帧泵、外设服务）与 **权限/入口分裂**；直播端当前路径相对轻。

## 4. 优化建议（按优先级，已按反馈修订）

### 4.1 关于「一致性 / 稳定再提交」与 24 秒、改分场景

**你的判断成立**，需在计划里明确写清边界：

- **「连续 N 帧整帧完全一致再发送」** 与 **24 秒每秒变化** 天然冲突：若门禁写成全字段相等，会要么发不出、要么延迟堆叠，历史上也出过类似问题。
- **`framesStableEnough` 类逻辑**（比分/节次相同 + 时钟/24s 在有限 delta 内）本意是容忍时钟抖动，但仍可能在 **回表、24s 突然置 14/24、节间暂停** 等场景与真实规则打架，需要极谨慎的用例矩阵，不适合作为「默认必开」的硬门槛。
- **比分 ±1、短窗多数表决** 在 **清零后重设、大比分跳变** 的业余/线下场景会 **降低可用性**，与当前产品优先级不符；若未来要做，也应 **默认关闭** 或仅针对「明显 OCR 鬼畜」（如单帧瞬间变三位乱码）做极窄规则。

**若仍要在「误识别」与「实时性」之间加一层，建议优先放在采集端，且遵守：**

1. **不要用「整帧 key 连续相等」作为唯一放行条件**；24s、全场时钟应视为「允许单调递减或规则内跳变」的字段，与比分字段解耦考虑。
2. **对比分**：优先用 **原始 OCR 字符串层** 的防抖（例如同一 ROI 在极短时间内 `rawText` 从 `8` 闪成 `0` 再回 `8` 才丢弃中间帧），而不是用「相对上一帧的步长」约束业务比分。
3. **直播端**：**不增加** 短窗表决、不重算历史帧；维持现有「解码成功即分发 + 已有 100ms `setData` 节流」，避免与录屏/相机抢主线程。

**结论**：原计划第 2 条「恢复 `_shouldCommitFrame` 或 Live 侧表决」不作为推荐默认方案；长时稳定性见 §4.2。

### 4.2 核心：采集端长时运行稳定性（2–5 小时）

优化重心建议放在 **Collector**（及微信基础能力边界），方向性清单（实施时再拆任务）：

- **VK / OCR 会话**：长时间运行后的 `session` 失效、无回调、内存增长；是否需要定时温和重建会话、或错误计数达阈值后重建（需实测避免闪断 BLE）。
- **`onCameraFrame` / 泵定时器**：确认无泄漏（定时器、闭包引用 listener）；页面切后台/锁屏策略与提示（小程序后台相机会停）。
- **BLE Peripheral**：连接断开后 `notify` 失败重试风暴；`_server` 生命周期与 `onStopTap` / 异常路径是否总能释放；长时间连接是否需心跳或状态机避免半连接。
- **热与降频**：高温降亮度、降低 OCR 泵频的可选策略（产品可接受略慢刷新但不能崩）。
- **日志**：长时问题依赖现场日志，关键路径打序列号/阶段标记，便于对齐「第几节、断线前后」。

### 4.3 核心：直播端不增加负担

- **保持** `BLE_DATA_UPDATE` → 轻量解码 → 节流 `setData` 的现有模型。
- **避免** 在 Live 增加：缓冲队列、多帧历史、复杂状态机、额外定时器驱动的 UI 对齐逻辑。
- **权限解耦**（与 `enableEnhanceRender` 分离）属于 **分支判断变简单**，不必然增加运行时成本。

### 4.4 解耦 Live「自动记分」与 `enableEnhanceRender`（仍推荐）

与稳定性不冲突：用 `autoSyncWhitelisted`（可与 sync-lab 同源）控制「能否进入自动记分」，**不把** 蓝牙记分绑在增强渲染机型上。

### 4.5 入口策略（替代「改文案」）

- **可选**：仅当用户命中与 sync-lab 相同的白名单（或统一能力位）时，Live 页 `onPeriodLongPress` 才展示/响应自动记分；非白名单用户走现有节次长按逻辑或不弹出该能力，**普通用户无感**。
- 与「改文案」二选一即可满足「不误导」目标。

### 4.6 工程杂项

- **>255 分**：已确认不支持，不列入路线。
- **broadcaster `_formatClockTime`**：`data.getMinutes()` → `d.getMinutes()` 为纯调试页 bugfix，对 Live 无负载影响；可择机修。

### 4.7 可选体验（非稳定性核心）

- Central 断线重连、白名单服务端下发等，仍可作为后续迭代，不与「直播端减压」冲突。
